# PageTalk Mermaid 总览方案设计

## 1. 背景

在多模型回答场景下，用户在一轮提问结束后，会得到多个模型的独立回答。当前界面适合逐列阅读，但缺少一个面向整轮回答的整体概览能力。

本方案目标是在用户提问对应的回答全部完成后，允许用户点击一个按钮，异步生成并查看一张 Mermaid 图，用来概览：

- 用户提问
- 所有模型的回答
- 基于这些内容生成出的结构化总结与 Mermaid 图

## 2. 本次方案已确认的决策

### 2.1 生成链路

采用两阶段生成：

1. 先总结
2. 再基于总结生成 Mermaid

这样比一步到位更稳定，能降低以下问题：

- 图结构发散
- 关键信息遗漏
- Mermaid 语法不稳定
- 多模型观点分歧表达不清

### 2.2 展示方式

点击按钮后直接复用现有 Mermaid 预览框进行展示，不新增独立的图表展示容器。

### 2.3 绑定关系

Mermaid 总览严格绑定到“用户消息后的第一条 model 结果”。

含义是：

- 每一条用户消息只对应自己这一轮回答的 Mermaid 总览
- 生成 Mermaid 时，只使用这条用户消息后面紧邻的那条 `model` 结果
- 如果该 `model` 结果是多模型结果，则从其中的 `multiModelResponses` 提取所有模型回答
- 不混入后续追问、后续轮次回答或其他用户消息的结果

这样可以保证一张 Mermaid 图只服务于一轮问答，避免轮次串扰。

## 3. 用户体验设计

### 3.1 按钮位置

在用户消息的 `<div class="message-actions">` 中新增一个按钮，名称暂定为：

- `Mermaid 总览`

该按钮挂在用户消息上，而不是挂在单个模型回答上。原因是它表达的是“这一轮问题的整体概览”，不是某个模型自己的结果。

### 3.2 按钮显示条件

第一版建议只在多模型回答轮次下显示。

即：

- 用户发起提问
- 该轮回答对应的是多模型结果
- 用户消息操作区显示 `Mermaid 总览` 按钮

单模型轮次先不显示，避免语义过弱。

### 3.3 按钮交互状态

按钮需要支持以下状态：

- `idle`
  - 尚未生成
  - 点击后开始后台异步生成
- `generating`
  - 正在生成
  - 按钮显示 loading 态
  - 不允许重复触发
- `ready`
  - 已生成成功
  - 点击后直接打开 Mermaid 预览框
- `error`
  - 生成失败
  - 按钮显示失败态
  - 点击后允许重试

### 3.4 交互流程

#### 首次点击

如果图还没生成：

1. 点击 `Mermaid 总览`
2. 按钮切换为 `generating`
3. 后台异步调用指定模型
4. 生成成功后状态变为 `ready`
5. 本次点击即可直接弹出 Mermaid 预览框

#### 后续点击

如果图已经生成：

1. 点击 `Mermaid 总览`
2. 直接弹出 Mermaid 预览框

#### 失败时

如果生成失败：

1. 按钮进入 `error`
2. 可点击重试

### 3.5 重新生成策略

本次采用方案 A：

- 用户消息操作区只保留一个 `Mermaid 总览` 按钮
- 当总览图已生成时，点击按钮直接打开现有 Mermaid 预览框
- `重新生成` 操作不放在消息操作区
- `重新生成` 按钮只出现在 Mermaid 预览框内

这样做的目的：

- 避免在消息操作区堆叠过多按钮
- 把“查看”和“重新生成”放在同一语境下处理
- 用户先看到当前图，再决定是否需要重生成

### 3.6 方案 A 的失败回退

当用户在 Mermaid 预览框中点击 `重新生成` 时：

1. 后台再次执行“两阶段生成”
2. 如果生成成功，则用新图替换当前预览
3. 如果生成失败，则保留旧图继续展示
4. 同时提示失败原因，但不让用户丢失上一版可用结果

这条规则很重要，因为总览图属于派生内容，用户常常会连续尝试多次直到满意。失败时保住旧图，体验会更稳定。

## 4. 生成流程设计

### 4.1 第一阶段：总结

输入内容：

- 用户提问
- 所有模型的回答
- 设置中配置的“总结提示词”

输出内容：

- 一份结构化总结文本

建议总结结果至少覆盖：

- 用户问题的核心意图
- 各模型的主要观点
- 模型之间的共识
- 模型之间的分歧
- 最适合做图的结构线索

### 4.2 第二阶段：生成 Mermaid

输入内容：

- 用户提问
- 所有模型回答
- 第一阶段产出的总结结果
- 设置中配置的“Mermaid 绘图提示词”

输出内容：

- 仅 Mermaid 源码

对模型输出应增加明确约束：

- 只返回 Mermaid 代码
- 不返回解释性文字
- 不包裹 Markdown 说明段落
- 优先使用易于阅读的 Mermaid 图类型

### 4.3 图类型策略

第一版不强制固定图类型，但可在提示词中鼓励模型根据内容选择，例如：

- `mindmap`
- `flowchart`
- `graph`

如果后续发现模型输出不稳定，可以进一步收敛为固定图类型。

## 5. 数据模型设计

建议将 Mermaid 总览数据挂在用户消息对象上，因为入口按钮位于用户消息操作区，状态天然属于这条用户消息。

推荐结构如下：

```js
userMessage.mermaidOverview = {
  status: 'idle' | 'generating' | 'ready' | 'error',
  linkedResponseId: '对应的多模型结果 messageId',
  generatorModel: 'provider::model',
  summaryPromptSnapshot: '生成时使用的总结提示词快照',
  diagramPromptSnapshot: '生成时使用的 Mermaid 提示词快照',
  summaryText: '第一阶段的总结结果',
  mermaidCode: 'Mermaid 原始源码',
  generatedAt: 0,
  errorMessage: ''
}
```

### 5.1 为什么挂在用户消息上

这样做有几个直接好处：

- 入口按钮就在用户消息上，状态读取最直接
- 一条提问只对应一份 Mermaid 总览，语义最自然
- 会话保存与恢复时可以随 `chatHistory` 一起保留
- 重新生成或删除时，失效范围更清晰

### 5.2 linkedResponseId 的作用

`linkedResponseId` 用于记录这份 Mermaid 总览绑定的是哪一条 `model` 结果，便于：

- 会话恢复时重新定位
- 回答重生成时判断是否需要失效
- 删除某个回答轮次时一起清理

## 6. 与现有聊天数据结构的关系

当前多模型回答在历史中可视为：

1. 一条 `user` 消息
2. 紧随其后的一条 `model` 消息

其中这条 `model` 消息内部包含：

- `parts`
- `multiModelResponses`
- `modelOrder`

因此 Mermaid 生成时的数据来源应为：

- 当前用户消息文本
- 当前用户消息后第一条 `model` 消息的 `multiModelResponses`

而不是全局扫描整段 `chatHistory`。

## 7. 状态流转设计

### 7.1 初始状态

用户消息创建时初始化：

```js
mermaidOverview = {
  status: 'idle'
}
```

### 7.2 生成中

点击按钮开始生成后：

```js
status = 'generating'
```

### 7.3 成功

当总结和 Mermaid 均完成，且 Mermaid 能通过本地校验后：

```js
status = 'ready'
```

同时写入：

- `summaryText`
- `mermaidCode`
- `generatedAt`
- `generatorModel`
- prompt 快照

### 7.4 失败

如果任一阶段失败，或 Mermaid 本地渲染校验失败：

```js
status = 'error'
errorMessage = '失败原因'
```

## 8. Mermaid 结果校验

在标记为 `ready` 之前，建议先做一次本地 Mermaid 校验或试渲染。

校验通过：

- 保存源码
- 状态置为 `ready`

校验失败：

- 状态置为 `error`
- 不展示错误图

第一版建议先做“失败即报错”，不自动补救。

后续可扩展为：

- Mermaid 渲染失败时，自动发起一次“修复 Mermaid 语法”的二次调用

但这不属于第一版范围。

## 9. 设置项设计

建议在现有设置页的“通用设置”中新增一张设置卡片，名称暂定：

- `Mermaid 总览设置`

卡片包含以下字段：

### 9.1 生成 Mermaid 的模型

字段：

- `Mermaid 生成模型`

说明：

- 用于选择负责“总结 + Mermaid 绘图”的模型
- 复用当前项目已有的模型来源
- 只展示当前已配置且可用的模型

### 9.2 总结提示词

字段：

- `总结提示词`

说明：

- 用于第一阶段总结
- 支持多行文本
- 允许用户自定义总结风格与结构

### 9.3 Mermaid 绘图提示词

字段：

- `Mermaid 绘图提示词`

说明：

- 用于第二阶段生成 Mermaid
- 支持多行文本
- 允许用户约束图类型、图层次、节点风格与输出格式

### 9.4 设置存储

建议与现有通用设置一起存储在同步存储中，便于多端一致。

## 10. 缓存与失效规则

Mermaid 总览属于“基于某轮回答生成的派生数据”，因此必须有明确的失效规则。

### 10.1 需要失效的情况

以下场景需要清空当前用户消息上的 Mermaid 缓存：

- 该轮多模型回答被重新生成
- 该轮中的某个模型回答被删除
- 该用户消息被删除
- 该轮绑定的 `model` 结果被删除

失效后：

- `status` 回到 `idle`
- 清空 `summaryText`
- 清空 `mermaidCode`
- 清空 `errorMessage`

### 10.2 不强制失效的情况

以下场景不强制清空历史 Mermaid：

- 设置中的 Mermaid 模型变更
- 总结提示词变更
- Mermaid 绘图提示词变更

原因是：

- 历史结果是当时配置下生成的快照
- 新配置应只影响未来生成

为保证可追溯性，建议保存 prompt 快照与生成模型信息。

## 11. 会话保存与恢复

因为 Mermaid 总览数据挂在 `chatHistory` 的用户消息对象上，所以应与聊天会话一起保存和恢复。

恢复会话时应满足：

- 如果 `status === ready`，按钮直接可查看
- 如果 `status === error`，按钮显示失败态，可重试
- 如果 `status === idle`，按钮显示可生成态
- 恢复后再次点击时，直接使用保存的 `mermaidCode`

第一版无需保存 SVG，只保存 Mermaid 源码即可，展示时临时渲染。

补充约束：

- 恢复旧会话后，如果某条消息已经有 `ready` 状态的 Mermaid 总览，点击后直接打开现有 Mermaid 预览框
- 预览框中的 `重新生成` 只对 Mermaid 总览生效
- 普通消息正文里的 Mermaid 图，仍然只支持放大预览，不出现 `重新生成`

## 12. 历史记录兼容与迁移策略

本方案要求兼容用户浏览器中已经存在的旧历史记录。

这些旧记录通常不包含新增的 `mermaidOverview` 字段，因此兼容策略采用“向后兼容 + 懒升级”，而不是启动时做全量强制迁移。

### 12.1 兼容原则

- 旧历史记录中没有 `mermaidOverview` 字段时，不报错
- 不在加载历史记录时强制重写旧数据
- 不要求用户先迁移历史记录才能使用该功能
- 只有在用户实际使用 Mermaid 总览功能时，才为对应消息补齐新字段

### 12.2 旧记录的默认处理方式

当恢复旧会话时，如果某条用户消息没有 `mermaidOverview`：

- 默认视为 `idle`
- 即视为“尚未生成 Mermaid 总览”
- 不影响原有聊天记录展示

也就是说，旧数据缺少该字段不会阻塞聊天恢复流程。

### 12.3 按钮显示不依赖新字段是否存在

对于旧历史记录，是否显示 `Mermaid 总览` 按钮，不应依赖该消息是否已经拥有 `mermaidOverview` 字段，而应在运行时动态判断：

1. 当前是否是一条 `user` 消息
2. 该消息后面是否存在第一条对应的 `model` 结果
3. 这条 `model` 结果是否包含 `multiModelResponses`

如果满足上述条件，即使是旧记录、即使没有 `mermaidOverview`，也可以显示按钮，并允许用户生成 Mermaid 总览。

### 12.4 懒创建新字段

对于旧会话，用户第一次点击 `Mermaid 总览` 按钮时，再为该条用户消息懒创建：

```js
message.mermaidOverview = {
  status: 'generating'
}
```

后续随着生成完成，再逐步补齐：

- `linkedResponseId`
- `generatorModel`
- `summaryPromptSnapshot`
- `diagramPromptSnapshot`
- `summaryText`
- `mermaidCode`
- `generatedAt`
- `errorMessage`

这种方式的优点是：

- 不污染用户未使用过的旧记录
- 不增加初始化阶段风险
- 不需要编写一次性迁移脚本

### 12.5 为什么不做启动时全量迁移

第一版不建议在加载应用时扫描并改写所有历史记录，原因包括：

- 风险更高，容易误改旧数据
- 会增加初始化逻辑复杂度
- 历史记录量较大时会增加性能负担
- 一旦迁移逻辑有误，回滚成本更高

因此本方案优先选择“读时兼容、用时补齐、保存时自然落盘”的策略。

### 12.6 保存与恢复行为

兼容策略下，会话保存与恢复应表现为：

- 旧记录如果从未生成过 Mermaid，总体保持原样
- 旧记录一旦生成过 Mermaid，之后保存时就会自然包含 `mermaidOverview`
- 下次恢复该会话时，可以直接根据 `mermaidOverview.status` 恢复按钮状态

即：

- 有 `mermaidOverview` 的记录，按新结构恢复
- 没有 `mermaidOverview` 的记录，按旧结构兼容恢复

### 12.7 验收标准

历史兼容完成后，应满足：

1. 旧历史记录可以正常打开，不报错
2. 旧历史记录中的多模型轮次可以显示 `Mermaid 总览` 按钮
3. 旧历史记录首次点击按钮时可以成功生成 Mermaid
4. 生成成功后再次保存该会话，新字段能被持久化
5. 下次恢复该会话时，已生成 Mermaid 的按钮状态和内容可以继续使用

## 13. 与现有 Mermaid 展示能力的关系

项目已经具备以下能力：

- Mermaid 代码渲染
- Mermaid 放大预览模态框
- Mermaid 主题切换与重渲染

因此本需求的重点不是“新增 Mermaid 能力”，而是新增：

- 针对多模型轮次的生成入口
- 两阶段调用编排
- 数据缓存
- 用户消息级状态管理

## 14. 第一版边界

为了降低首版复杂度，建议将范围限制为：

- 仅支持主聊天面板
- 不支持划词助手
- 仅支持多模型轮次
- 仅通过手动点击触发生成
- 不自动预生成
- 不自动修复 Mermaid 语法
- 不新增独立图表区域，统一使用现有 Mermaid 预览框

## 15. 推荐文案方向

### 14.1 按钮文案

可考虑以下文案之一：

- `Mermaid 总览`
- `生成总览图`
- `查看总览图`

实际显示可根据状态变化：

- `idle`: `生成总览图`
- `generating`: `生成中...`
- `ready`: `查看总览图`
- `error`: `重试生成`

### 14.2 设置项文案

建议使用：

- `Mermaid 总览设置`
- `Mermaid 生成模型`
- `总结提示词`
- `Mermaid 绘图提示词`

## 16. 验收标准

完成后应满足以下行为：

1. 多模型轮次的用户消息操作区可见 `Mermaid 总览` 按钮
2. 首次点击时，按钮进入后台异步生成流程
3. 生成流程按“两阶段：先总结，再生成 Mermaid”执行
4. 生成成功后，点击按钮可直接打开现有 Mermaid 预览框
5. Mermaid 数据与该用户消息绑定，不串到其他轮次
6. 回答重生成、删除回答、删除提问时，Mermaid 缓存能正确失效
7. 会话恢复后，已生成的 Mermaid 仍可查看
8. 设置页支持配置 Mermaid 生成模型、总结提示词、Mermaid 绘图提示词

## 17. 后续可扩展项

本方案落地后，后续可继续扩展：

- 支持单模型轮次生成 Mermaid
- 支持自动预生成
- 支持 Mermaid 语法自动修复
- 支持切换不同图类型策略
- 支持在预览框中查看“总结文本 + Mermaid 图”
- 支持导出 Mermaid 源码
